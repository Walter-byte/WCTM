# PPR-1: implemented data flow and privacy/security inventory

Repository audit at `2754958` plus the PPR-1 connector changes. This describes code and configuration, not a certification of a live merchant site. Public name: **WCTM — Telegram Store Manager for WooCommerce, by Walterbyte**. Technical `wctm` identifiers remain unchanged.

## Flow

```text
WooCommerce order/product data and local webhook credentials
  -> WordPress WCTM connector (registration, eight WooCommerce webhooks)
  -> HTTPS WCTM backend (M8 HMAC check against exact raw body)
  -> PostgreSQL WebhookEvent JSON and Order/Inventory projections
  -> Redis/BullMQ ID-only jobs and operational rate-limit keys
  -> backend-selected authorized manager -> bot internal API -> Telegram Bot API

WCTM browser/account and Woo REST configuration -> backend -> PostgreSQL
PostgreSQL -> local custom-format dump + SHA-256/metadata -> rclone -> OneDrive
```

The backend also calls the WooCommerce REST API over HTTPS for connection checks, reconciliation, order writes, search context and inventory bootstrap. The bot receives Telegram updates, forwards authorized operations through the internal backend API, and sends replies through Telegram. No product telemetry or tracking cookie was found in the connector. The bot is stateless and database-free; Telegram itself retains messages according to its own service behavior.

## Controls and findings

- **Verified controls:** backend encrypts Woo REST and webhook secrets; hashes registration/link/plugin credentials; tenant-scoped application reads and authorization; webhook HMAC before JSON persistence; Telegram private-chat and membership checks; audit metadata allowlist; central log redaction; loopback-only backend and private PostgreSQL/Redis ports; restricted `wctm_runtime`; backup checksum and remote content verification. Source: `backend/src/common/encryption`, `backend/src/tenant`, `backend/src/webhooks`, `backend/src/telegram`, `backend/src/common/audit`, `backend/src/common/logging`, `docker-compose.yml`, `scripts/ops`.
- **API and error boundary:** normal Store summary selects omit encrypted credentials; plugin registration returns connection material once to the token holder; Telegram operational routes require the bot service key and current chat/membership authorization. Backend webhook failures use bounded diagnostic codes; bot transport logs emit error class and update ID, not request/response bodies. This does not establish a complete formal non-disclosure proof for every future endpoint.
- **PPR-1 local improvement:** WordPress Privacy Policy Guide text; explicit GPL identity; plugin-local uninstall removes options and exactly matching webhook records when WooCommerce is available. No personal-data exporter/eraser hook was added: the connector itself holds only store/credential configuration, not locally collected customer/order records. WooCommerce owns its own customer/order data and export/erasure integration.
- **Pilot blocker PPR-1.1:** Signed full Woo webhook JSON is kept in `WebhookEvent.payload` without expiry, and full Woo billing/shipping/line-item objects are copied to Order snapshots. Extra customer PII and arbitrary Woo metadata can persist. Reducing this safely needs an approved field contract, handling for existing rows/backups, and regression proof for order/inventory workflows. Do not claim current storage is minimal.
- **Pilot blocker PPR-1.2:** Store/Tenant delete is soft deletion; plugin deactivation, uninstall and Telegram unlink do not delete service-side orders, events, audit rows, chat history or backups. Store deletion does not clear encrypted credentials. Define an authenticated service deletion/export/retention procedure with legal and DR exceptions before merchant pilot onboarding.
- **Pilot blocker PPR-1.3:** Redis AOF and BullMQ jobs have no explicit completion/failure cleanup or queue retention rule; PostgreSQL application rows and off-site backup copies have no reviewed lifetime. Define tested retention and deletion schedules, including provider copies and journal logs, before processing real pilot customer data.
- **Pilot blocker PPR-1.4:** WordPress-side connector/webhook secrets are plaintext in WordPress/WooCommerce database storage (autoload disabled, hidden in UI). Confirm merchant-host access/backup controls and document rotation after uninstall or compromise. No blanket WordPress at-rest encryption claim is justified.
- **Pilot blocker PPR-1.5:** Backup scripts verify integrity but do not encrypt the database dump before OneDrive transfer. Access policy, provider encryption/retention and whether application-level backup encryption is required need A/operator approval before real pilot data is copied off-site.
- **Operational boundary:** Uninstall cannot contact WCTM or erase Telegram; if WooCommerce APIs are unavailable, local WordPress options are removed but connector webhooks may remain. Merchant/operator must inspect WooCommerce webhooks and rotate service credentials. Deactivation retains all material and can leave hooks active.

## Disconnect, deletion and licensing

- **Deactivation:** no cleanup; connector options and WooCommerce hooks remain, so webhook delivery can continue.
- **Uninstall:** local options are deleted; currently matching connector-owned WooCommerce webhooks are deleted when WC APIs are available. No outbound request. This is not SaaS account deletion.
- **Store delete / Tenant delete:** OWNER/ADMIN Store soft delete and OWNER Tenant soft delete gate active access, but preserve rows, snapshots, credentials and backups. No hard-delete/export workflow is present.
- **Telegram unlink:** confirmed private-chat action revokes chat authorization and marks the account deleted; historic rows and Telegram messages remain.
- **WordPress plugin license:** `GPL-2.0-or-later`, with header/readme and `LICENSE.txt`. The shipped plugin contains one first-party PHP file plus readme/license; no bundled third-party library or asset was found. WooCommerce/WordPress APIs are runtime integration, not redistributed code. The separate backend/bot/SaaS remain proprietary and are not relicensed by this plugin decision. Public identity and license are approved under D-034. WordPress's [plugin header guidance](https://developer.wordpress.org/plugins/plugin-basics/header-requirements/) and [licensing statement](https://wordpress.org/about/license/) support the plugin metadata.
